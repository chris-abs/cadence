# Meal planning — product spec and data model

**Status: Draft — awaiting owner decisions.** Assumes the "Default v1" in `docs/PLAN.md` §6.
Every assumption that the owner has not confirmed is marked **[D#]** and listed in §7.

A family keeps its own recipe book with structured ingredients (quantity, unit, name).
Parents fill a weekly plan, one dinner per day by default, with a recipe or free text
("leftovers", "eating out"). From a week's plan a parent generates one shopping list that
merges duplicate ingredients, adds manual items, and anyone in the family ticks items off
on their phone in the shop. Children can see everything and tick items; they cannot edit.

## 1. What the legacy `feature/meals` branch tells us

The branch (6 files, ~1,040 lines: entities, request models, schema, a 686-line repository;
no handlers, service or tests) reworked the `main` draft. Both were read for nouns only.

| Legacy concept | Verdict | Why |
|---|---|---|
| `meal_ingredient` rows (name, quantity, unit, category) instead of `main`'s JSONB blob | **Keep** (core) | The owner already moved to rows; it is what makes merging possible |
| Shopping list generated by `SUM(quantity) GROUP BY name, unit` | **Keep, fix** | Right idea. Grouped on raw strings ("Onion" ≠ "onion "), no unit conversion, could never regenerate (unique per plan) |
| One shopping list per plan, items with `is_completed` | **Keep** as one list per week | Matches the default; add manual items (`main` had them, the branch lost them) |
| `adult_count` / `child_count` per day, child = 0.5 portion | **Simplify** to optional `servings` per entry **[D5]** | Same intent, one number; the 0.5 rule is a hidden magic constant |
| `prep_time`, `cook_time`, `instructions`, `description`, `image_url` | **Keep** | Standard recipe fields; image deferred to slice 6.4 |
| `main`: `meal_type` on plan rows, `notes`, `source` recipe on list item | **Keep** as `slot`, `note` | Slot as a field is exactly the "more later" seam |
| `category` on ingredients / list items (aisle grouping) | **Defer** **[D8]** | Useful in the shop, but per-ingredient typing is tedious; better as a per-family name→aisle memory later |
| `meal` table with **no `family_id`** (a global catalogue) | **Drop** | Every row in Cadence is family-scoped |
| `macros`, `dietary_info`, allergens, cuisine/subcategory, `meal_option`, primary/secondary/side ingredient types | **Drop** | Nutrition and taxonomy are out of scope (PLAN Q17); search filters for a household's 50 recipes are overkill |
| `meal_plan` header with `start_date`/`end_date` + `meal_plan_day` (one meal per day, unique) | **Drop the header** | A week is a date range, not a row. Removes a "create plan" step and the one-per-day limit |
| `meal_plan_assignee` (who cooks) on `main` | **Drop** | Out of scope (Q17) |
| `is_deleted`/`deleted_at`/`deleted_by` on every table, `pg_trgm` GIN indexes | **Drop** | PLAN: no blanket soft-delete, no trigram |
| `VARCHAR(36)` ids with `INTEGER` FKs and Go `int` ids | **Fix** | Native `uuid` (UUIDv7 from Go) everywhere |

Placeholder client page (`cadence/meals/index.tsx`): a Monday–Sunday grid of free-text inputs.
Confirms the mental model: **a week of dinners, typed quickly**. Free text must stay first-class.

## 2. v1 scope

Acceptance criteria are written to become handler or component tests.

### Slice 6.1 — Recipes

| Story | Acceptance criteria |
|---|---|
| R1. As a parent I add a recipe with ingredients | Name required (1–120 chars, trimmed). Optional description, instructions, servings, prep/cook minutes, source URL. 0–100 ingredient rows. Saved recipe is returned with ingredients in entered order. |
| R2. I enter ingredients quickly | Each row: optional quantity, optional unit from the fixed list (§4.2), required name, optional note ("finely chopped"). Unit without quantity → 422. Quantity accepts `1.5`, `1/2`, `1 1/2` (parsed client-side, sent as a decimal > 0). Name field autocompletes from the family's existing ingredient names. |
| R3. Anyone finds a recipe again | List sorted by name, case-insensitive substring search on name. Another family's recipe id returns 404, never 403. |
| R4. I edit a recipe | PUT replaces all fields and the whole ingredient list in one transaction. Existing plan entries show the new name; existing shopping lists do not change until regenerated (and show "out of date"). |
| R5. I delete a recipe | Detail shows "Used in N upcoming meals" first. After delete, those plan entries remain as free text with the recipe's last name; nothing else is lost. |

### Slice 6.2 — Weekly plan

| Story | Acceptance criteria |
|---|---|
| P1. Anyone sees this week | Default view is the week containing today (device local date), starting on the family's week-start day (default Monday **[D2]**). Each day shows its dinner entries. Prev/next week navigation. |
| P2. A parent puts a recipe on a day | Pick a recipe from search; entry stores `recipe_id` and a snapshot `title`. Optional servings and note. |
| P3. A parent types free text | "Leftovers", "Pizza night" saved with no recipe. Empty title → 422. |
| P4. A parent changes the plan | Move an entry to another date/slot, swap recipe/text, delete it. More than one entry per slot is allowed (e.g. main + side) **[D3]**, ordered by `position`. |
| P5. A child views the plan | Child sees the same week; add/edit/delete controls are absent and the API returns 403 for writes. |

### Slice 6.3 — Shopping list

| Story | Acceptance criteria |
|---|---|
| S1. A parent makes the week's list | "Make list" for a week creates it (or regenerates it). Lines come only from recipe entries in that week; free-text entries add nothing. |
| S2. Duplicates merge | Same normalised name + compatible unit sum into one line (`200 g` + `0.5 kg` onion → `700 g`). Incompatible units stay separate lines (`2` onions and `300 g` onion). Lines with no quantity merge to one line with no quantity ("salt"). Scaling: line quantity × `entry.servings / recipe.servings` when both set, else × 1. Each line lists its source recipes. |
| S3. Regenerate keeps work | Regenerating after a plan change: manual items untouched; generated lines with the same key keep their tick unless their quantity went up (then unticked); lines no longer needed are removed; new ones added. |
| S4. The list knows it is stale | GET returns `stale: true` when regenerating now would produce different lines; the UI shows "Plan changed — update list". |
| S5. Anyone adds a manual item | Parent adds "kitchen roll", optional quantity/unit. Manual items can be edited and deleted; generated lines can only be ticked **[D11]**. |
| S6. Anyone ticks items in the shop | `PATCH {checked: true/false}` is idempotent (set, not toggle) so two phones never fight. Records who ticked and when. Ticks visible on another device within 10 s without reload. Parent and child both allowed. |

### Not in v1

URL/recipe import; photos (slice 6.4, separate); nutrition, allergens, cuisine tags; pantry or
"already have"; cost; AI plans; who-cooks assignment; aisle grouping **[D8]**; offline mode and
push/WebSocket sync **[D9]**; breakfast/lunch/snack in the UI (model supports them **[D2]**);
copy/repeat a week; favourites/ratings; printing; child suggestions **[D7]**; recipe version
history; imperial display preferences; ingredient plural/synonym matching.

## 3. Roles

Owner has no extra meal powers; owner = PARENT throughout. All routes need a profile session.

| Action | PARENT | CHILD |
|---|---|---|
| View recipes, plan, shopping lists | ✓ | ✓ |
| Create / edit / delete recipe | ✓ | 403 |
| Create / edit / move / delete plan entry | ✓ | 403 **[D7]** |
| Generate / regenerate list | ✓ | 403 |
| Add / edit / delete manual item | ✓ | 403 **[D7]** (cheap to flip) |
| Tick / untick any item | ✓ | ✓ |
| Change family week-start day | ✓ | 403 |

The matrix test covers every row × {PARENT, CHILD, family-session-only (401), other family (404)}.

## 4. Data model

Conventions for every table: `id uuid PRIMARY KEY` (UUIDv7, set in Go), `family_id uuid NOT NULL
REFERENCES family(id) ON DELETE CASCADE`, `created_at`/`updated_at timestamptz NOT NULL DEFAULT
now()`, `set_updated_at()` trigger (baseline migration), RLS enabled with no policies (0001).
No soft delete. Assumes identity tables `family(id)` and `profile(id, family_id)` from M3.

**Family scoping:** where the client supplies a foreign id (`recipe_id`, `list_id`), a
composite FK `(family_id, x_id) → parent(family_id, id)` makes cross-family links impossible
in the database, not just in Go. Parents therefore carry `UNIQUE (family_id, id)`. Profile
references (`created_by`, `checked_by`) are set from the session, so a plain FK is enough.

### 4.1 Tables

**`family` (identity table, one new column)**

| Column | Type | Notes |
|---|---|---|
| `week_starts_on` | `smallint NOT NULL DEFAULT 1` | `CHECK (week_starts_on BETWEEN 0 AND 6)`, 0 = Sunday, 1 = Monday **[D2]** |

**`recipe`** — the family's recipe book.

| Column | Type | Constraints |
|---|---|---|
| `name` | `text NOT NULL` | `CHECK (char_length(name) BETWEEN 1 AND 120)` |
| `description` | `text NOT NULL DEFAULT ''` | ≤ 2,000 (Go validation) |
| `instructions` | `text NOT NULL DEFAULT ''` | Plain text, one step per line; ≤ 20,000 **[D12]** |
| `servings` | `smallint NULL` | `CHECK (servings BETWEEN 1 AND 50)` — base for scaling **[D5]** |
| `prep_minutes`, `cook_minutes` | `smallint NULL` | `CHECK (… BETWEEN 0 AND 1440)` |
| `source_url` | `text NULL` | http(s), ≤ 2,048; a link, not an import |
| `image_key` | `text NULL` | S3 key, slice 6.4; unused until then |
| `created_by` | `uuid NULL REFERENCES profile(id) ON DELETE SET NULL` | |

Indexes: `UNIQUE (family_id, id)`; `(family_id, lower(name))` for the sorted list and `ILIKE` search.
Names are not unique: two "Chilli" recipes are allowed.

**`recipe_ingredient`** — one row per ingredient line; replaced wholesale on recipe PUT.

| Column | Type | Constraints |
|---|---|---|
| `recipe_id` | `uuid NOT NULL` | `FOREIGN KEY (family_id, recipe_id) REFERENCES recipe(family_id, id) ON DELETE CASCADE` |
| `position` | `smallint NOT NULL` | `UNIQUE (recipe_id, position)`, 0-based |
| `quantity` | `numeric(10,3) NULL` | `CHECK (quantity > 0)` |
| `unit` | `text NULL` | `CHECK (unit IN (<codes in §4.2>))`; NULL = a count ("2 onions") |
| `name` | `text NOT NULL` | `CHECK (char_length(name) BETWEEN 1 AND 80)`, as typed for display |
| `name_key` | `text GENERATED ALWAYS AS (lower(regexp_replace(btrim(name), '\s+', ' ', 'g'))) STORED` | Merge key |
| `note` | `text NOT NULL DEFAULT ''` | Preparation, not part of the key ("diced") |
| | | `CHECK (unit IS NULL OR quantity IS NOT NULL)` |

Indexes: the unique `(recipe_id, position)`; `(family_id, name_key)` for autocomplete.
Rationale: rows (not JSONB) so SQL/Go can aggregate; `note` keeps "diced" out of the merge key.

**`meal_plan_entry`** — one thing to eat in one slot on one date. No week/plan header row.

| Column | Type | Constraints |
|---|---|---|
| `date` | `date NOT NULL` | Plain calendar date, no timezone |
| `slot` | `text NOT NULL DEFAULT 'dinner'` | `CHECK (slot IN ('breakfast','lunch','dinner','snack'))` **[D2]** |
| `position` | `smallint NOT NULL DEFAULT 0` | Order within a slot; no uniqueness (several per slot) **[D3]** |
| `recipe_id` | `uuid NULL` | `FOREIGN KEY (family_id, recipe_id) REFERENCES recipe(family_id, id) ON DELETE SET NULL (recipe_id)` (Postgres 15+) |
| `title` | `text NOT NULL` | `CHECK (char_length(title) BETWEEN 1 AND 120)`; free text, or recipe name snapshot |
| `servings` | `smallint NULL` | `CHECK (servings BETWEEN 1 AND 50)` **[D5]** |
| `note` | `text NOT NULL DEFAULT ''` | ≤ 500 |
| `created_by` | `uuid NULL REFERENCES profile(id) ON DELETE SET NULL` | |

Indexes: `(family_id, date)`; `(recipe_id)` for "used in N meals" and the SET NULL cascade.
Rationale: *recipe OR free text* is one column being NULL, not a type enum — `title` is always
present, so a deleted recipe degrades to free text with zero special cases. API responses show
the live recipe name when `recipe_id` is set; `title` is refreshed to it on every entry write.

**`shopping_list`** — one per family per week **[D4]**.

| Column | Type | Constraints |
|---|---|---|
| `week_start` | `date NOT NULL` | `UNIQUE (family_id, week_start)`; covers `week_start … week_start + 6` |
| `generated_at` | `timestamptz NULL` | NULL = only manual items so far |
| `source_hash` | `text NULL` | SHA-256 of the computed generated lines at last generation |

Indexes: the unique key, plus `UNIQUE (family_id, id)`. The list stores its own range, so
changing `week_starts_on` later never moves old lists. The server rejects a `week_start` whose
weekday ≠ `family.week_starts_on` (422).

**`shopping_item`**

| Column | Type | Constraints |
|---|---|---|
| `list_id` | `uuid NOT NULL` | `FOREIGN KEY (family_id, list_id) REFERENCES shopping_list(family_id, id) ON DELETE CASCADE` |
| `origin` | `text NOT NULL` | `CHECK (origin IN ('generated','manual'))` |
| `name` | `text NOT NULL` | 1–80 chars |
| `name_key` | generated, same expression as `recipe_ingredient` | |
| `quantity` | `numeric(12,3) NULL` | `CHECK (quantity > 0)` |
| `unit` | `text NULL` | Same unit check; for generated lines the merge unit (§4.2) |
| `sources` | `text NOT NULL DEFAULT ''` | Generated only: "Lasagne, Chilli" (display snapshot) |
| `checked_at` | `timestamptz NULL` | Ticked when not NULL |
| `checked_by` | `uuid NULL REFERENCES profile(id) ON DELETE SET NULL` | |

Indexes: `(list_id)`; `UNIQUE (list_id, name_key, coalesce(unit, '')) WHERE origin = 'generated'`
— the merge key, used as the upsert target on regeneration.
Rationale: generated lines are **snapshots**, not live views of recipes. That keeps ticks stable
while recipes change, and makes "what's on the list" exactly what the shopper sees.

### 4.2 Units and merging

Units are a fixed list (OpenAPI enum + DB `CHECK`; adding one = one small migration):

| Group | Codes | Merge rule |
|---|---|---|
| Mass | `g`, `kg`, `oz`, `lb` | Convert to g (1, 1000, 28.35, 453.6) |
| Volume | `ml`, `l`, `tsp`, `tbsp`, `cup` | Convert to ml (1, 1000, 5, 15, 250 **[D10]**) |
| Count-like | NULL (each), `clove`, `slice`, `tin`, `pack`, `bunch`, `pinch` | Merge only with the identical unit |

Generation (Go, pure function, table-tested; SQL only fetches rows):
1. Collect ingredients of recipe entries with `date` in the week, scaled per S2.
2. Group by `(name_key, merge unit)`. If every contribution used the same unit, keep it
   (3 tbsp stays 3 tbsp); otherwise sum in base unit and display g→kg / ml→l at ≥ 1000.
3. Display name = most frequent original `name` in the group; round to 2 dp, trim zeros.
4. In one transaction with `SELECT … FOR UPDATE` on the list: upsert by merge key (keep
   `checked_at` unless quantity increased), delete generated lines not produced, set
   `generated_at` and `source_hash`. Manual items are never touched.

Normalisation is deliberately shallow (case, whitespace). "Tomato" vs "tomatoes" will not merge;
autocomplete from existing `name_key`s is the v1 mitigation. Manual items are not merged with
generated lines (shown separately).

### 4.3 Recipe edited or deleted

| Event | Plan entries | Shopping lists |
|---|---|---|
| Recipe renamed / ingredients edited | Show new name (live join) | Unchanged; `stale: true` until regenerated |
| Recipe deleted | `recipe_id` → NULL, `title` keeps last name (now free text) **[D6]** | Unchanged; on regenerate its lines drop out |
| Plan entry deleted | — | `stale: true` |
| Profile deleted | `created_by` → NULL | `checked_by` → NULL, tick kept |

Staleness = recompute lines for the week and compare their hash with `source_hash` (cheap at
family scale; avoids tracking every edit with timestamps).

## 5. API sketch

All under `/api`, profile session required (401 otherwise), ids are uuids, dates `YYYY-MM-DD`.
Other-family ids → 404. Validation → 422 with field errors. Concurrent recipe edits: last write wins.

| Method | Path | Purpose | Who |
|---|---|---|---|
| GET | `/recipes?q=` | List summaries (id, name, times, ingredient count) | P, C |
| POST | `/recipes` | Create with ingredients | P |
| GET | `/recipes/{id}` | Full recipe + ingredients + `upcomingUses` count | P, C |
| PUT | `/recipes/{id}` | Replace recipe and all ingredients | P |
| DELETE | `/recipes/{id}` | Hard delete (204) | P |
| GET | `/ingredient-names?q=` | Up to 10 distinct names for autocomplete | P |
| GET | `/plan?from=&to=` | Entries in range (≤ 42 days), with recipe name | P, C |
| POST | `/plan/entries` | Create entry (`recipeId` or `title`) | P |
| PATCH | `/plan/entries/{id}` | Move date/slot/position, change recipe/title/servings/note | P |
| DELETE | `/plan/entries/{id}` | Remove entry | P |
| GET | `/shopping-lists/{weekStart}` | List + items + `stale`; 404 if none yet | P, C |
| POST | `/shopping-lists/{weekStart}/generate` | Create or regenerate (§4.2) | P |
| POST | `/shopping-lists/{weekStart}/items` | Add manual item (creates list if missing) | P |
| PATCH | `/shopping-items/{id}` | `{checked}` (P, C); name/qty/unit on manual items (P) | P, C |
| DELETE | `/shopping-items/{id}` | Manual items only; generated → 422 | P |
| PATCH | `/family` (identity) | Includes `weekStartsOn` | P |

Units and slots are enums in `api/openapi.yaml`, so no endpoint is needed for them.

## 6. Screens

| Screen | Route | Key content | Empty / loading / error |
|---|---|---|---|
| Week plan (meals home) | `/meals` | 7 day rows, today highlighted, entries per day, prev/next week, "Shopping list" button | Empty day: "Nothing planned" + add (parent). Skeleton rows. Error: retry banner, keep last data |
| Add/edit entry | sheet over week | Search recipes or type text; servings; note | No recipes yet: free text still works + "Add a recipe" link |
| Recipe list | `/meals/recipes` | Search box, A–Z list | "Add your first recipe" (parent) / "No recipes yet" (child). No search hits: "No match for …" |
| Recipe detail | `/meals/recipes/$id` | Ingredients, instructions, "Add to plan", edit/delete | 404: "Recipe not found" + back |
| Recipe editor | `/meals/recipes/new`, `…/$id/edit` | Fields + ingredient rows (qty, unit, name, note), reorder, add row on Enter | Inline 422 errors per row; unsaved-changes prompt |
| Shopping list | `/meals/shopping/$weekStart` | Unticked first, ticked collapsed at bottom; stale banner; add-item bar | No list: "Make list from this week" (parent) / "No list yet" (child). Offline: "Not saved — retrying" |

Phone in the supermarket (the screen that matters most):
- Whole row is the tap target (≥ 48 px), large text, one-handed: add bar and actions at the bottom.
- Tick is optimistic, moves the row to "Done" with a 5 s undo toast; failed requests retry and
  show a persistent banner rather than silently reverting.
- Polls every 5 s while visible (TanStack Query `refetchInterval`) and refetches on focus/reconnect.
- Requests a screen wake lock where supported so the phone does not sleep mid-shop.
- Recipe editor on phone: ingredient row stacks qty+unit over name; numeric keyboard for qty.

Ranked by impact on the data model. **$$$** = expensive to change once data exists.

| # | PLAN Q | Question | Recommended default | If the owner chooses otherwise |
|---|---|---|---|---|
| D1 | 9 | Structured or free-text ingredients? | Structured, quantity/unit optional | Free text: drop qty/unit columns and merging; list becomes concatenation. Switching back later means parsing every recipe by hand. **$$$** |
| D4 | 12 | One list per week or one running list? | Per week | Running list: `shopping_list` becomes one per family, `week_start` goes, regeneration must track which week contributed which lines (`source_week` on items). **$$** |

| D9 | 13 | Live sync and offline in the shop? | 5 s polling, online only | Live: SSE endpoint + list version. Offline: local queue, conflict rules, service worker; best decided before 6.5. **$$** |
| D7 | 14 | Children: view+tick only, or add items / suggest meals? | View + tick | Add items: one matrix row. Suggestions: new `status` on entries + review UI. **$** / **$$** |
| D12 | — | Instructions as plain text or numbered steps? | Plain text, one step per line | Steps table or `text[]`: small migration while recipes are few. **$** |
| D13 | 16 | URL import, photos in v1? | Manual only; photos in 6.4 (`image_key` reserved) | Import: parser + "review ingredients" UI, big effort, no model change. |
| D14 | 17 | Confirm out of scope: pantry, nutrition, cost, AI, who-cooks | Confirmed out | Each is a new table and slice; none is blocked by this model. |

## 8. Risks and deliberately deferred

- **Name matching** is the main quality risk: plurals and synonyms produce duplicate lines.
  Autocomplete is the v1 mitigation; a per-family alias table can come later without migration pain.
- **Composite FK `ON DELETE SET NULL (recipe_id)`** needs Postgres 15+; local is 17, confirm the
  Supabase project version (PLAN §3).
- **Identity dependency:** assumes `family` / `profile` tables and the `week_starts_on` column land
  in M3 or a meals migration; agree which before writing migration 1.
- **Recipe PUT replaces ingredients:** ingredient ids are not stable. Nothing references them in
  v1; if anything ever does (e.g. per-ingredient notes on the list), switch to a diff.
- **"Today"** is computed on the device; two family members in different timezones may briefly
  disagree about the current week. Acceptable for a household.
- **Polling** is ~12 requests/min per open list; fine for one family, revisit with SSE (D9).
- **Last-write-wins** on recipes; add an `updated_at` precondition (409) if two parents ever clash.
- Deferred: images (6.4), aisle grouping, offline, live push, import, search beyond `ILIKE`,
  copy-a-week, unit display preferences.
